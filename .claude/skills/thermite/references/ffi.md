# thermite-ffi

A C ABI over Thermite's math library: batch (array-at-a-time) functions exposed
as `extern "C"`, dispatched at runtime to the best backend, callable from any
language with a C FFI. Crate type is `cdylib` (name `thermite`), producing
`thermite.dll` / `libthermite.so`.

> **Who this is for.** If you write **Rust**, ignore this crate -- depend on
> `thermite` directly and call the generic API; you get inlining and type safety
> the FFI can't. This reference is for calling Thermite from **C or another
> language** with a C FFI. You first build (or obtain) the shared library below,
> then link against it and use the C API.

## Building the library you link against

The shared library is built from the Thermite source with the **nightly**
toolchain (the FFI crate is the one part of Thermite that requires nightly). The
build generates the header with `cbindgen` from the crate's config and uses the
`release-ffi` profile with `-nostdlib` (this mirrors the project's CI in
`.github/workflows/ffi_artifacts.yaml`):

```bash
# 1. Generate the C header
cbindgen -q --config crates/thermite-ffi/cbindgen.toml --crate thermite-ffi --output thermite.h

# 2. Build the shared library (RUSTFLAGS strips the std runtime)
RUSTFLAGS="-C link-arg=-nostdlib" \
  cargo +nightly build --profile release-ffi -p thermite-ffi --target x86_64-pc-windows-msvc
```

(Use `--target x86_64-unknown-linux-gnu` for `libthermite.so`.) Output lands in
`target/<target>/release-ffi/`: `thermite.dll` (+ `thermite.dll.lib` import lib on
Windows) or `libthermite.so`. The `release-ffi` profile is `opt-level=3`, fat LTO,
`codegen-units=1`, `strip`, `panic=abort`. On Windows CI the dll is then compressed
with `mpress`.

> The header is generated straight from `cbindgen.toml` + the crate -- there is no
> `cargo expand` step in the current pipeline.

## C API shape

Two ways to call: global functions, or a caller-held vtable.

```c
#include "thermite.h"

// --- global init + free functions ---
void        thermite_init(void);                              // best backend, default policy
void        thermite_init_with_policy(ThermitePrecisionPolicy);
void        thermite_init_vtable(Thermite *vtable, ThermitePrecisionPolicy);  // fill a caller struct
const char *thermite_backend_name(void);                      // e.g. "x86_v3"
ThermiteDenormalResult thermite_disable_denormals(void);
ThermiteDenormalResult thermite_enable_denormals(void);

// Policy enum: DefaultPolicy = 0, HighPerformance = -1, HighPrecision = 1
```

The `Thermite` struct is a vtable of function pointers plus `name` and `alignment`.

**Naming scheme** (generated by the `decl_methods!` macro in `src/lib.rs`): every
batch op exists in an `f32` and an `f64` form, plus an **argument-shape suffix**
that is always present:

- shape suffix: `_v` (one vector in, one out), `_vv` (two vector inputs), `_vs`
  (vector + scalar), `_vvv`, etc.
- **f32**: the element marker `f` goes right before the shape -> `<op>f_<shape>`
  (e.g. `addf_v`, `sinf_v`, `sin_cosf_vv`, `clampf_vs`).
- **f64**: no `f` -> `<op>_<shape>` (e.g. `add_v`, `sin_v`, `clamp_vs`).
- vtable fields use exactly those names; the free functions prefix `thermite_`
  (e.g. `thermite_addf_v`, `thermite_add_v`).

Signature: `void op(size_t len, const T *in..., T *out...[, T scalars])`. In-place
is allowed (same pointer for in and out); overlapping-but-offset aliasing is not.

Representative usage (from `crates/thermite-ffi/examples/bench.c`):

```c
Thermite *vtable = malloc(sizeof(Thermite));
thermite_init_vtable(vtable, HighPerformance);
printf("backend: %s\n", vtable->name);

// f32 sin+cos: one input, two outputs (the actual KERNEL_FUNC in bench.c)
vtable->sin_cosf_vv(len, in, sin_out, cos_out);
// f32 sin in place: one in, one out
vtable->sinf_v(len, data, data);
vtable->enable_denormals();
free(vtable);
```

Or without a vtable, after `thermite_init()`, call the free functions
`thermite_sinf_v(len, in, out)`, `thermite_addf_v(len, a, b, out)`, etc.

## What's exported

Generated by the `decl_methods!` macro; roughly the whole real-math surface, each
in an f32 form (`<op>f_<shape>`) and an f64 form (`<op>_<shape>`). Base operation
names include:

- **Arithmetic / rounding**: add, sub, mul, div, rem, min, max, abs, signum, round,
  floor, ceil, trunc, fract, next_up, next_down, mul_add/mul_sub/nmul_add/nmul_sub.
- **Core/transcendental**: inverse_sqrt, reciprocal, sin, cos, tan, sin_cos (2 out),
  sinh, cosh, tanh, sinh_cosh, asin, acos, atan, asinh, acosh, atanh, exp, exp2,
  exp10, exp_m1, ln, ln_1p, log2, log10, log (base), cbrt, powf, atan2, hypot,
  sin_pi/cos_pi/tan_pi/sinc.
- **Real math**: wrap_angle, angle_diff, to_degrees, to_radians, lerp, smoothstep,
  smootherstep, inverse_smoothstep, step, clamp, gaussian, powi.
- **Special**: erf, erfc, logistic_sigmoid, tgamma, lgamma, beta, erfinv.

The shape suffix encodes the argument arity: `_v` (one vector), `_vv` (two
vectors, e.g. `atan2`, `hypot`, `beta`), `_vs` (vector + scalar, e.g.
`clampf_vs(len, x, min, max, out)`), `_vvv`, etc. Multi-output ops like `sin_cos`
take two `*mut` outputs.

## Crate features

`high_performance` / `high_precision` (default on) gate those policy code paths;
`disable_dispatch` inlines everything for max speed at the cost of large binaries;
`ignore_denormals` / `preserve_denormals` set denormal handling.
